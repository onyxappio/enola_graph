# Config-enumeration fusion: comparison and retirement

Two implementations of the same optimization existed. Stage16's is kept; the
prototype built in this dispatch is retired. This file records why, and what the
prototype contributed before being withdrawn, so the evidence survives the
retirement.

Nothing here is a performance acceptance. No timing, benchmark or Product run was
performed for this comparison, and none of it bears on Stage16's unresolved RSS
signal.

## The duplication

One `tsConfigInputs` call enumerated the repository tree twice: once through
`collectTSAliasRoots`, a recursive `overlayReadDir` descent, and once through
`overlayWalkDir`. Both descend from the repository root under the same prune
(dot-prefixed names and `tsSkipDirs`, root exempt) and neither excludes
`testdata`, so one enumeration can answer for both.

Stage16 (base `49b486b`, configwalk.go in the unmerged candidate) fuses them
with the **alias traversal primary**: `tsAliasWalk.walk` recurses via
`overlayReadDir` and collects config candidate paths through `collectFile`, which
the caller reads after the walk. The prototype (`022fbfd`, retired) fused them
with the **walk primary**: `overlayWalkDir` carried a per-directory alias
decision through an extracted `aliasRootAt`.

Same mechanism, mirrored direction. The prototype was designed without
discovering Stage16 first; that was the error, and it is recorded rather than
glossed.

## Fallback comparison

| | Stage16 | prototype (retired) |
|---|---|---|
| root not a real directory | declines | declines |
| root refused by directory policy | declines, via `enumErr` side effect | declines, via explicit `Allowed` check |
| any listing error in the tree | declines for the whole call | keeps fusion |
| probe attached to the context | declines | keeps fusion |
| alias-before-extends read order | preserved | **not preserved** |

No universal runtime-cost bound was measured for either implementation, and none
is claimed. Declining is not free: it adds the lstat, and in Stage16's
listing-error case it also collects candidates that are then discarded. The two
rows where the prototype is less conservative are real but narrow, and the
read-order row is a genuine deficit on the prototype's side: Stage16 defers
config reads until after the traversal
specifically so that every alias read still precedes every extends read, which is
the order the two original passes produced. The prototype interleaves them per
directory. That alone disqualifies it as a drop-in replacement.

The probe decline is benign today, verified rather than assumed: the only
non-test `withOverlayProbe` call is `discovery.go:83`, its context is local to
`newDiscovery`, and `newDiscovery` never calls `tsConfigInputs`. The live callers
are `ExtractSession` (`session.go:807`, caller-supplied context) and two
`context.Background()` callers. It is not free, though — it means no probe-based
test can observe the fused path, and a future caller attaching a probe upstream
of `ExtractSession` would lose the optimization silently.

## What the prototype contributed, and what was already covered

Stage16 already carries a stronger equivalence mechanism than goldens: an in-tree
verbatim copy of the pre-change enumeration (`oracleTSConfigInputs`, generated by
`oracle-refresh.py`) compared on every fixture by `compareConfigInputs`. Against
that, the 13-fixture oracle is **additive in two places only**:

1. **Probe-record coverage.** `compareConfigInputs` compares returned candidate
   sets. It does not compare probe observations at all. The oracle pins
   `probe_reads`, `probe_stats`, `probe_dirs` and the separate alias-probe maps
   against a fixed baseline captured at `02e5e2d`.
2. **Root outside the policy root with a readable tsconfig.** Stage16's
   `TestConfigWalkMatchesUnderScopeExclusions` excludes a *subtree*; no existing
   test covers a root the directory policy refuses while
   `Policy.ClassifyDependency` still admits its tsconfig as an explicit external
   dependency (`internal/graphinput/policy.go:898`). Fixture
   `out_of_scope_root_readable_config` is that case.

Everything else the oracle asserts was already pinned by Stage16's own tests,
with a stronger mechanism: symlinked root (`TestConfigWalkMatchesForSymlinkedRoot`),
symlinked children, unreadable directory, scope exclusions, hidden root, config
add and remove, partial listing error, and fusion-without-probe. The oracle is
kept as belt-and-braces plus the two additions above, not as new coverage of
those cases.

## Oracle freshness, confirmed by root

Stage16's `oracleTSConfigInputs` is generated, so it can go stale against the
function it mirrors. `oracle-refresh.py` is not in the source tree (it lives in
`/tmp/enola-stage16-configwalk`), so this worker could not run its `--check`
mode and said so rather than asserting the oracle was in sync. Root ran it:

  python3 -B /tmp/enola-stage16-configwalk/oracle-refresh.py --check
  # cwd /tmp/enola-config-enum/stage16-coverage

Exit 0 - the in-tree oracle matches a verbatim lift of `49b486b`. Root reviewed
the read-only `--check` branch before running it (`msg_72bce60ae8fe`).

## Correction carried into Stage16

`walkDirDescendsInto`'s comment claimed its `os.Lstat` "is the same one
`filepath.WalkDir` performs ... so asking here observes nothing the walk did not
already observe". That is wrong, and wrong in the direction that understates
cost: `filepath.WalkDir` performs its own lstat and cannot be handed this one, so
the declining path pays two, and on the fused path there is no walk to share with
at all. Operation accounting for this enumeration must include **one added lstat
per `tsConfigInputs` call**. The comment is corrected; no code changed.

## Operation counts, and their limit

On the 13 fixtures the prototype reduced directory listings from 64 to 38. Those
are exact `Scope.ReadDir` invocation counts plus WalkDir listings *derived from
the documented WalkDir contract* — not measured syscalls — and they exclude the
added lstat per call. They were produced with scratch counters in
`inputscope/scope.go` that are not part of any patch.

Stage16 already holds better evidence for the same mechanism: 27.6% fewer bytes
and 32.1% fewer allocations per call on clean Product. The prototype's counts add
nothing to that, and neither figure is CLI latency evidence.

## Retirement

`patch01-config-fusion.patch` (prototype, sha256
`7445ac663f4c5035e9e02b9f938e90ae733a0582cc0ca70103e71be356959084`) is retired as
a candidate and retained as a recorded alternative only. Its scratch tree,
production-only verification worktree and counters are kept unchanged; no further
work goes into it.
