# Independent resident harness review

Read-only review, 2026-09-21. No benchmarks, tests, builds, or Product mutations performed; no timings are endorsed. References below use `docs/benchmarks/product-delta-2026-09-21/` unless an absolute/internal path is given. Production APIs were inspected read-only; after the coordinator announced the frozen oracle, changes.go and resident.go were verified identical to /tmp/enola-resident-stage-source. The coordinator separately reports an unchanged driver build passed; this review did not run that build.

## Blocking acceptance issues

1. **P1 — Ignored-input watch probes can pass without observing the edit.** `resident.py:120-126` sleeps 100 ms, sends no expected paths in watch mode, and accepts an empty drain as success. The driver only waits for delivery when request paths are present (`resident-driver.go.txt:113-156`); `FileChangeSource.Drain` explicitly does not promise a filesystem barrier (`internal/graphsession/changes.go:123-125`). A delayed/missed notification therefore produces a green zero-work result. **Patch:** include the ignored path as an expected observed event for watch mode, wait with a bounded timeout, and assert delivery/coverage separately from semantic work. If production filters events before queuing, expose a delivery watermark or use a documented backend barrier rather than assuming sleep proves receipt. Also exercise lock add/rename/remove and explicit repository exclusions: current probes only append to an existing pnpm lock and one PNG (`resident.py:78-84`), silently skipping absent inputs. PNG name alone does not establish all-consumer opacity; classify probe eligibility explicitly and record skipped cases.

2. **P1 — True watcher checks accept fallback reconciliation without the expected event.** The wait loop exits whenever `batch.Reconcile != ""` (`resident-driver.go.txt:136,152-154`), even if `complete()` is false. Python records `Reconciled` but never asserts expected observed paths or loss-free coverage (`resident.py:95-106,127-128`). Thus an overflow/coverage failure can reconcile correctly and still be accepted as the local watcher edit benchmark. **Patch:** return the complete batch metadata and an explicit expected-event-observed flag; require observed source path, Covered=true, continuous epoch/watermark, and no unexpected reconciliation for body/structural local-edit acceptance. Keep fallback measurements, but label them separately and fail the local fast-path acceptance. This harness measures request-triggered ApplyChanges using real OS events, not the production `Watch` loop/debounce (`internal/graphsession/changes.go:267-322`); retain that distinction in reports.

3. **P1 — Work accounting excludes coverage catch-up from reported parsed totals.** Driver correctly includes catch-up duration and archives each result (`resident-driver.go.txt:69-92`), but Python exposes only the first `result` and prints its ParsedFiles (`resident.py:95,106`). Startup can legitimately reconcile again after external config registration (`internal/graphsession/changes.go:325-329,412-413`); source duplicate events can also do additional work. **Patch:** retain primary/catch-up results and publish aggregate ParsedFiles, Stats, Work counters, fallback reasons and reconciliation count for every operation, especially startup. For no-op checks, require a nonempty expected Work schema instead of `.get('Work', {})` (vacuous success at `resident.py:104-105`), assert catch-up ParsedFiles=0 and unchanged generations explicitly, and ensure no unaccounted catch-up results. The current generation-change panic is useful and should remain.

4. **P1 — “Fresh initial” is not enforced.** Both harnesses reuse existing root/state directories (`resident.py:5,112,115`; `multifile.py:5,85-86`). `OpenSession` loads/replays existing state (`internal/graphsession/session.go:129-149`). Reusing an output root can therefore benchmark warm reconciliation as resident initial, or restart observer reconstruction from a nonzero base. **Patch:** reject existing state/metrics/consumer artifacts unless an explicit resume mode is requested; create a unique run/context namespace, require initial BaseGeneration=0 and successful initial publication, and validate repeat>=1 (currently repeat=0 bypasses multifile acceptance entirely). Do not delete arbitrary user directories automatically.

5. **P1 — Cancellation can leave mutated inputs/processes.** Normal exceptions/timeouts have useful cleanup (`resident.py:143-150`; `multifile.py:98`), but default Python SIGTERM terminates without running finally, leaving edits/checkouts and separately sessioned children alive. In resident cleanup, a killpg race/cleanup error can also bypass all restoration (`resident.py:145-148`), and one restore failure skips remaining files. `run()` starts its sampler and Popen outside a cleanup guard covering creation (`resident.py:43-46`; `multifile.py:45-48`). **Patch:** install SIGTERM/SIGINT handling that enters cleanup, use nested try/finally/ExitStack to attempt every restore and close, tolerate ProcessLookupError, terminate/wait owned process groups before restoring, and preserve the primary error. Restore the original symbolic branch as well as SHA when applicable (`multifile.py:7,77-78,98` currently leaves an originally attached checkout detached). Broker/observer ownership is external: document and enforce launcher cleanup, rather than claiming these scripts stop them.

## Additional fixes needed before performance claims

6. **P2 — Wire matching is timestamp/context-only, despite an available run ID.** `resident.py:15-23,98-99` and `multifile.py:17-25,65-66` accept the first context frame with observer receipt time after operation start. A replay/backlog frame can satisfy this; neither requires a nonempty hash or target-generation match. `OnlineResult.Result.RunID` exists (`internal/graphsession/session.go:54-58`); observer rows include `run_id`. **Patch:** match resident Result.RunID exactly, add structured CLI run/generation output for multifile, require valid digest/expected generation, and validate fresh observer readiness/isolated stream before measuring. Archive observer source and binary hash: the scripts currently record producer provenance but not the oracle (`resident.py:11`; `multifile.py:13`). I inspected `/tmp/enola-product-bench-expanded-source/cmd/benchobserver/main.go`; that source's identity with the supplied observer binary is not established by these harnesses.

7. **P2 — Timing and memory presentation needs explicit boundaries.** Producer wall clocks finish after process exit or driver response (`resident.py:53,95-97`; `multifile.py:55`), while consumer completion is separate; that is appropriate. However resident initial launches before `online()` runs `streaminfo()` (`resident.py:91,114-116`), so an observer-info subprocess on the critical reporting path can inflate initial wall time and its stream delta can omit early bootstrap messages. The CLI seconds also include state sampling shutdown and a final directory scan (`resident.py:52-53`; `multifile.py:54-55`). **Patch:** capture producer completion immediately at wait/response, sample pre-run stream state before launch, and report instrumentation overhead separately. Extract lifetime RSS from `r*-resident.log` into metrics after exit (`resident.py:129-131` currently leaves it only in raw logs), aggregate repeated spreads and delta/initial ratios, and separately report fresh-CLI no-change from resident idle. `resident.py --old` is parsed but never used, and `--cold`/`--initial-only` are inert in both scripts; implement or reject/remove these flags so invocation does not imply measurements it never runs.

## Checks that are sound, with limits

- **Context sequencing:** resident completes initial/noops/body/structural before switching to cold contexts or the next fresh main context (`resident.py:116-138`). Multifile completes initial/noop/delta before the next context (`multifile.py:86-94`). This is compatible with the inspected observer's single-active-context eviction (`/tmp/enola-product-bench-expanded-source/cmd/benchobserver/main.go:11`); there is no current return-to-evicted-context defect.
- **Independent wire oracle:** inspected observer consumes JetStream, applies `graphsession.Consumer`, AckSyncs, and hashes sorted owner/node/edge rows (`observer main.go:4,14-15`); this tests transported state, though it shares the production consumer implementation. It is not merely comparing producer in-memory snapshots. Both harnesses compare each changed result to a separate cold target under the configured profile.
- **ACK boundary:** current NATSSink.Publish waits for JetStream publish acknowledgment (`internal/graphstream/nats.go:149-158`); producer completion therefore includes broker acknowledgments. Observer `broker_end_ns` is the server timestamp, not the instant the producer received its final ACK. `consumer_end_ns` precedes normalization/file fsync in the inspected observer (`main.go:15`), so label it apply/ACK completion, not completed hash-artifact availability.
- **Startup coverage:** source starts before baseline, driver calls CoverSessionInputs, drains/applies coverage reconciliation, and includes it in elapsed time before responding. This follows the current public API contract. Do not subtract that catch-up from fresh startup; add its work to the totals as above.
- **No-op scope:** stream sequence deltas detect published events on an isolated broker, and resident Work assertions are stronger than CLI parsed/generation checks. Already-running idle evidence cannot establish near-zero fresh CLI startup, and fresh CLI no-op here does not expose scan/hash/persistence counters.

Root should patch the harnesses, then run cheap syntax/driver-build checks against the finalized API before scheduling isolated acceptance measurements. This review itself changed only this report.
