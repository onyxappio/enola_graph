## Confirmed blockers

### 1. Generated legacy ignores do not establish exact same source scope (high; blocks same-scope acceptance claim)

`benchscope.go.txt:22-26,38-51,58-67` preserves candidate TestGlobs and translates excluded paths only into legacy Ignore. Pinned old `internal/engine/engine.go:1005-1029` puts ignored files in AllNames before ignoring them, and explicitly retains ignored test files in testFiles; line 514 runs reference extraction on that list. Candidate `internal/engine/engine.go:1145-1150` applies graph policy before collecting names or tests. Thus an excluded `src/foo.test.ts` remains a parsed reference input in old Enola and is absent in candidate. This is an input-scope difference, not just transitive-property/lock-fact semantics. Legacy independent side reads are an additional known limitation that ignores cannot solve.

`HARNESS.md:99` currently overclaims “Source selection is aligned”; that claim is not supported by the translator. `cli.py:106-110` verifies only the old config's repo, so a stale/generated-for-another-profile or arbitrary ignore/extractor configuration can also be accepted without scope evidence. `multifile.py:112-118` improves revision-specific configuration/provenance but retains the translator mismatch. Archive actual selected input inventories (including reference-only and side-input classes), reconcile the supported differences, or explicitly label legacy timings as approximate-scope/legacy-workload comparisons that do not close AGENTS same-scope acceptance. Merely hashing the binary/config does not prove scope equality.

### 2. Resident cleanup failure can report successful acceptance (medium)

`resident.py:190-197` catches stop/restoration failures, prints CLEANUP ERRORS, and does not raise. If all checks pass but restoring Product's source/lock/media fails, the script exits successfully while leaving the checkout changed. This contradicts `HARNESS.md:63-65`'s restoration statement and the task's restoration requirement. Attempt every cleanup as now, then propagate aggregated cleanup failures (while retaining an original failure). Other scripts propagate restoration errors instead.

### 3. Resident console parse/fallback summary omits catch-up work (medium; reporting blocker)

`resident.py:126-131` and `resident_history.py:120-125` correctly retain aggregate parsed/work/stats/fallback/reconciliation metrics, but their DONE lines (`resident.py:150`, `resident_history.py:140`) still print only primary `res['ParsedFiles']` / primary reconciliation and fallback. A request with catch-up parsing therefore prints fewer parses than it performed. Consumers/report generators must use aggregate fields, and the console should print those fields too. JSON evidence itself is retained and is not invalidated by this display issue.

## Limitations and required reporting qualifications

- **CLI timing includes polling quantization:** `cli.py:64-83`, `multifile.py:67-86` and corresponding cold helpers start before sampler/thread/output setup, wait with `Popen.wait(timeout=600)`, and timestamp after the timeout-based wait returns. CPython POSIX timeout waits poll with bounded sleeps; this overstates actual process completion by up to roughly 50 ms plus setup/scheduling. A bounded three-repeat probe of Python children sleeping 20/80/200 ms returned total waits about 73–84/139–144/255–262 ms (includes child startup, so not an isolated estimate of polling alone). This is conservative for multi-second measurements, but cannot substantiate near-zero fresh CLI latency precisely. Prefer blocking wait with an independent timeout watchdog, or label parent-observed wall timing and retain `/usr/bin/time` real time separately. No under-reporting of broker acknowledgment completion was found.
- **Resident history checkout-through-apply label includes observation/report overhead:** `resident_history.py:163-164` computes it after online(), whose lines 130-140 wait for consumer hash, query stream info, and save/print. Primary `seconds` is captured at driver response and driver seconds include catch-up; use these definitions explicitly. Do not compare the broader checkout-through-apply metric as pure ApplyChanges time.
- **Historical configuration scope:** every script writes an explicit external config (`multifile.py:34-38`, `resident_history.py:34-38` etc.). `pkg/bootstrap/graph.go:38-54` treats it as overriding root discovery, and scope-config is copied once. A history that changes repository Enola config is therefore not a benchmark of adopting that changed root config unless the harness explicitly models that transition. Package manifests/TS config changes can still be exercised. Product exclusions require an explicit appropriate scope fragment; default invocation does not import repository config automatically.
- **Untracked inputs/provenance:** clean checks use `--untracked-files=no` (`*:28`), and provenance records commit/config/binary hashes but no complete semantic input digest/untracked manifest. Dedicated stable clones are required; HEAD alone does not prove identical effective inputs. This review did not inspect or mutate Product clones, so it does not assert an actual contamination in these runs.
- **Source-mode and native evidence:** queue mode is a cooperating-writer measurement, native driver is request-driven and excludes production watch debounce. These distinctions are correctly documented. Aggregate Work/Stats must remain separate from strict CLI startup claims.
- **Spread/ratio reporting remains external:** scripts record repeat rows but do not calculate medians/ranges or delta/initial ratios or enforce performance thresholds. Final reporting must provide those and distinguish legacy semantic workload, producer RSS, observed broker timestamps, and end-to-end completion. This is not a standalone performance-acceptance test.
