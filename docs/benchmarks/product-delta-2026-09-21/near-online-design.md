# Near-online Enola: implementation recommendation

Read-only architecture review, 2026-09-21. No source edits, tests, benchmarks, workers, commits or publication were performed. Reviewed current checkout (HEAD d086926aca80975dde34094e99c84cce59fb1cd6 plus substantial existing working changes), AGENTS.md, CONTRIBUTING.md, streaming contract, graphsession state/persistence/invalidation/ownership/session, TS session/config discovery, CLI entry point, relevant existing regression tests, and supplied profile logs. Another worker owns detector/config optimization; line locations may move as that work settles. Function names below identify change points. Supplied performance results are evidence from the coordinator, not measurements made here.

## Recommendation and feasibility

Implement a persistent single-writer graph session behind `graph watch`, with an explicit changed-input transaction API and bounded filesystem-event queue; retain today's content-hash reconciliation as the conservative fallback. Once proven, expose that session through local IPC so a new CLI can request an already-running session's generation/status/flush. Do not market a fresh CLI that skips validation as equivalent to this path.

Near-zero **resident idle** work is feasible: no repository walk, hash sweep, detector execution, JSON decoding, graph reconstruction, publication or checkpoint write when nothing is dirty. Near-online small deltas are feasible for audited local-file paths, but require incremental composition/index maintenance and delta persistence as well as event detection. A daemon alone removes startup work but does not remove the current whole-graph passes.

Near-zero **strict cold CLI**, with arbitrary mutable working-directory changes and no pre-existing monitor/change journal, is not feasible portably. The process must discover added/deleted paths and validate relevant bytes. A compact manifest or stat cache can reduce allocations and prioritize checks, but cannot prove unchanged contents. A persistent OS journal or external monitor can supply evidence across invocations only with validated coverage, continuity and recovery; that is a pre-existing monitor, not a free cold path. An explicitly immutable content-addressed input tree is another distinct mode; it does not describe today's dirty working-tree contract.

Generic portable event APIs also do not prove instantaneous disk equality merely because their userspace queue is empty. State the online result as complete through an observed event watermark and captured input versions. A strict request requiring all writes completed before request time needs a backend-supported flush/barrier covering those writes, a cooperating writer transaction, or full reconciliation. Do not substitute a quiet debounce timer for that guarantee. Silent loss on unsupported/network filesystems requires reconciliation; periodic audits provide eventual repair, not strict per-request equality.

## Profile evidence and remaining costs

Coordinator's corrected candidate: initial 11.526 s, noop 2.881 s, body 4.395 s, structural 4.841 s, with all 12 supplied equivalence checks passing. Body/initial is about 0.381; structural/initial about 0.420. These are not accepted near-online targets and are not a new repeated benchmark from this review.

The supplied profile-noop log totals 2.905 s: state decode/load 0.479 s for 58.2 MB; inventory 0.434 s over 45,105 names; detection 1.089 s; content/context inputs 0.519 s (9,030 file hashes, 90.6 MB); config fingerprint 0.173 s; extractor-need work 0.071 s; TS cache fact copying 0.093 s; remaining assembly about 0.030 s. Thus zero parses does not mean zero repository work.

The supplied profile-revert log totals 4.675 s, a different operation/sample from the body headline. It adds two TS passes (0.470 and approximately 0.484 s including assembly), whole-owner index/grouping 0.023 s, resolved publication 0.113 s for 89 owners, all-TS revalidation 0.116 s, pending-state writing stage 0.526 s and end/flush/promotion 0.103 s. Do not call the second pass a redundant parse without checking its affected owner: current code passes only the additional `need` set and merges its counters. Both passes nevertheless aggregate and compose the full TS graph. Each profiled pass spends about 0.165 s in composition/modules and 0.16 s on config discovery; main already contains `SessionHooks.SkipConfigPaths`, so that particular profile cost may be gone after the other worker's changes.

Even perfect detector/config tuning leaves fresh-process state load, inventory and hashing. Even resident detection leaves full TS aggregation, package-name discovery, owner grouping, all-record revalidation, 58 MB checkpoint rewriting, fsync and broker acknowledgments. These are the next bottlenecks, not justification for a larger delivery journal. No numeric latency promise is supportable until the root's harness measures them.

## Minimal implementation sequence

### 1. Separate lifetime from one replacement transaction

In `internal/graphsession/session.go`, split `Run` into an `OpenSession`-style lifetime (lock, identity binding, journal open/replay, pending recovery, state load) and an `ApplyChanges` operation. Keep `Run` as the strict one-shot wrapper using reconciliation, preserving existing CLI semantics. Change `Watch` from its current 1,500 ms ticker repeatedly calling `Run` to one live lifetime; retain lock ownership for that lifetime. Do not reuse the existing `session` struct directly without separating/resetting per-run mutable fields (`seq`, payloads, scopes, sources, publication errors and buffers).

Retain immutable committed `FileRecord`/`FileState` contributions and build runtime caches once: source and independent config inventories, per-extractor input memberships, hashes, framework/alias/package context, reverse imports, referenced-name subscribers, unresolved import candidates, owner facts and resolution candidates. Keep one committed view plus transaction-local replacements; do not mutate cached facts with composition passes. A no-change return must precede `reuseTSCache`, `cloneTagged`, allFacts assembly and publisher setup. `Result.Facts` currently exposes the whole graph and existing tests use it; preserve one-shot compatibility, but give online Apply a summary result and explicit/lazy snapshot accessor so every online response need not copy the graph.

A new CLI can later attach using a local socket/named pipe keyed by canonical checkout, state directory, repository/context, sink identity, extractor build and effective config. Do not start a second state owner on IPC failure; honor the existing lock. Reconnect to an existing session only when identities match. Report cold start/reconciliation separately from online request time.

### 2. Introduce a conservative change-source boundary

Add an internal interface returning bounded `ChangeSet` batches: changed paths and affected directories, old/new name information if known, monotonic local sequence, source epoch, coverage status and `mustReconcile` reason. Suggested operations are Start/Capture/Drain or Next, with a fake implementation for deterministic tests and an explicit full-reconcile implementation. This is a new interface proposal, not an existing facility.

Register watches before baseline traversal, collect events while scanning/hashing, then replay/drain changes until a valid baseline watermark is established. Recursive registration must cover newly created/moved-in directories and scan their subtree after registration; installing a root watch alone is not recursive on every platform. Parent-directory coverage must notice missing config slots, atomic replacement, deletion and restored files. Include directory-only semantic inputs such as empty asset directories. Track explicitly read external/extended configuration paths and relevant parent directories as well as the source tree. Match each discovery routine's semantics instead of copying the source ignore policy.

Hash the bytes of every event-dirty relevant input even if its stat tuple equals the previous tuple. Coalesce events to a dirty set and read the current bytes rather than trying to replay filesystem operations literally. A create/delete/rename storm is allowed to become one conservative directory rescan. Duplicate/reordered events are harmless; unknown rename pairing means deletion plus addition. An event whose content hash is unchanged updates observation metadata without graph events or generation advancement.

Errors, kernel/user queue overflow, missing watches, volume/root identity change, loss of journal continuity, unsupported filesystem behavior or uncertain external input coverage set `mustReconcile`; never drop the indication when dropping individual paths. On those paths run inventory plus content hashing plus config/context discovery. Reconcile on process restart unless an independently durable watcher proves a gap-free retained cursor with matching volume/root/coverage epoch. An in-memory sequence number persisted at shutdown cannot prove changes while the process was dead.

Bound dirty paths/bytes and in-flight generations. On queue overflow collapse to a sticky reconcile-required state, not an unbounded list. Keep the event reader responsive while parsing or broker delivery blocks. Debounce briefly with a maximum wait to avoid starvation; duration is a tuning parameter, not a correctness proof. Idle watch should have no polling-triggered analysis; an optional audit timer must be reported as repository work, separate from idle request latency.

### 3. Make audited single-file work proportional to affected inputs

Refactor `session.run` to accept the maintained inventory/hash/context view and changed paths, with today's scan path supplying the same interface. Update `filesToHash`, `extractorInputDigest`, `inventoryDigest`, `captureDeltaContexts` and `ownedExtractorContextNeed` to avoid scanning all names on known narrow changes. Initially retain their full implementations for fallback. Maintain per-extractor membership/hash indexes; avoid a home-grown XOR digest that loses multiplicity or permits cancelling changes. Version the persistent digest scheme if changed.

`plugin.DeltaInputs` describes content/name inputs and `DeltaContext` computes an opaque context digest; neither alone provides an observable dependency manifest for every detector or external read. Add explicit detector/context dependency descriptions (files, name predicates, directory discovery rules and external paths) for audited builtins. Inactive enabled detectors need invalidation too: a new marker can activate an extractor. Until audited, rerun the opaque detector/context or reconcile its scope; do not infer safety from `OwnsFile` or previously detected extractors. Preserve existing hidden-input coverage, including ignored manifest directories and Swift includes/assets. Reload effective Enola/client config and engine when those inputs change.

In `internal/extractors/tsextractor/session.go`, split `ExtractSession` into dirty-file extraction, contribution update, and derived composition. Reuse existing `extractFile`, whole-file `FileRecord`, GraphQL/gRPC/router contributions and immutable fact cloning where mutation is necessary. Avoid `parallel.MapFiles` over every cached file and concatenating all facts on each change. Cache `collectTSAliasRoots`, `collectPackageNames`, framework detection and knownFiles under their actual input versions. Maintain GraphQL/gRPC contributor counts/maps (including ambiguity) and synthetic module owner contributor counts. Use full composition and an explicit reason for contexts without an audited incremental dependency model, including current Angular fallback; retain initial streaming.

In `invalidate.go`, maintain reverse adjacency rather than rebuilding it in `reverseClose`; use a work queue to fixed point. Maintain name-to-referencing-owner and unresolved-spec indexes. Whole-file parsing is still required for any changed source; do not classify an edit as harmless by diff shape. `surfaceChanged` is a useful seed, not universal evidence that all derived rule inputs stayed constant. Changes to candidate identities, names, imports/re-exports, resolution preference, ambiguity, deletions, framework summaries and config must invalidate all dependent direct relationships. Where the current summaries cannot establish completeness, broaden. An unchanged local IO attribute at callers is deliberately not propagated.

In `owner.go`, replace global `buildIndex`/`groupOwners` on the fast path with removal/insertion of changed owner contributions and candidate buckets. Cache resolution subscriptions by target name and repo under `idIndex.resolve`'s exact ambiguity/identity rules. Changed candidate buckets require refreshing their referring owners even without import edges. Preserve occurrence multiplicity, deterministic contribution order, shared synthetic ownership and module reference counts. `addChangedRouteFiles` should consume changed composition outputs instead of diffing flattened old/new graphs; until then its full pass is a known residual cost. Compute complete affected owner scope (including composition owners) before resolved writes, retaining allowed scope growth semantics.

This can be delivered in stages: resident lifetime plus events first; incremental TS/index work next; bounded delta persistence next. Do not present the first stage alone as completion of the one-file latency goal.

### 4. Persist small transactions and serialize committed generations

`persist.go:writePendingState` rewrites the entire state. Add a versioned analysis-state delta log or per-file immutable blobs plus a small durable generation manifest; preserve old state import/migration and fork semantics. A delta transaction records changed/deleted file records, contribution/index metadata needed for recovery, input versions and base/target/run identity. The delivery journal is still the exact event payload authority; the analysis-state log serves a different purpose.

Order: capture inputs and derive transaction from exact committed generation; durably prepare the state patch and event payloads under current bounded publisher semantics; publish/flush through acknowledged End; durably commit/promote that patch; then expose new in-memory committed state and consume the corresponding dirty watermark. Crash recovery must find acknowledged End before promotion exactly as `recoverAcknowledgedPending` does today. Crash after End ack and before local commit must recover before creating the next generation. Never allow a no-change shortcut before outstanding replay/recovery.

Queue writes/events arriving during transaction A for B; do not clear a path whose last-dirty sequence exceeds A's capture boundary. B derives from A only after A commits, and merges inputs changed again while A ran. On a failed transaction retain/requeue its dirty set and immutable baseline; retry recorded broker identities with identical payloads or use a new incomplete run plus valid recovery path. Do not advance state on volatile queue admission. Bound patch-log and checkpoint space too; compaction uses an immutable committed snapshot and atomically installed/fsynced manifest. Checkpoint occasionally, rather than making every small delta write 58 MB; crash during compaction must keep a recoverable prefix. Adapt `Fork` checkpoint copying to include the committed patch chain or materialize a completed checkpoint under its existing lock.

For stable inputs, replace the all-TS read/hash loop near `revalidate_ts_records` with verification of captured dirty sources/context plus a valid event coverage watermark. This is safe only under the declared online guarantee. Under strict one-shot mode keep reconciliation/revalidation. If inputs change during capture, retry/abort the transaction or clearly commit its captured version then queue the later edit, consistent with the streaming contract; do not stamp the final disk hash onto earlier parsed bytes. Unknown non-TS disk reads preclude claiming a captured snapshot until instrumented or conservatively validated.

## Stat, hashes and Git: explicit limits

A cached `(size, mtime)` is insufficient; `TestSameSizeRestoredMtimeStillDirty` already demands detection. Adding ctime, device/inode/file ID and mode catches many common edits and atomic saves but does not provide a portable content identity: timestamp granularity, filesystem semantics, inode reuse, restored metadata and remote caching vary. Treat changed metadata as evidence to read; equal metadata is not proof to skip hashing in strict cold mode. The watcher path must hash a dirty path independently of stat equality. A same-stat fake-filesystem regression is useful to prevent accidental reliance on ctime on platforms where the existing test happens to pass.

Hash captured bytes once and bind records to those bytes. Pre/post stat checks can detect common races but do not prove absence of same-size concurrent rewrites; retry unstable reads, process subsequent events and limit the claim to captured versions. Directory mtimes do not propagate descendant content edits. Persist input membership and negative lookups so new configs and nearer lockfiles are detected. Read errors/permission changes are not deletion or a successful empty result.

Git can supply candidate paths for a main-revision transition, but cannot be the exclusive change source: untracked, ignored-but-semantic, unstaged/staged content, external config, index flags, submodules and detector-specific discovery differ from Git's tracked tree. Same HEAD does not mean same graph inputs; a commit-only HEAD move need not advance a graph generation if all analysis inputs match. Dirty state must remain independently versioned. Main revision updates should be one queued transaction with add/delete/rename/config candidates plus monitored working-tree changes, with broad reconciliation for an unmonitored checkout. Branch labels do not authorize applying a delta onto an unrelated base/context. Watch events do not imply an atomic checkout snapshot; use a caller transaction boundary where available or debounce/reconcile the resulting working tree and report the captured input versions.

## Meaningful validation for implementation owner

No tests run here. Extend, do not weaken, the existing tests named below and compare accumulated initial+delta consumer state with a fresh cold graph after every quiescent fixture revision, including properties, ownership, resolved/unresolved edges and duplicate occurrences.

1. Resident no-change after bootstrap: inject an empty *covered* change batch; counters assert zero inventory walks, stat/hash/source reads, detector/context scans, fact copies, parses, publication, state writes and generation change. Separate pending-recovery case must replay before reporting idle. Test many iterations to detect leaked per-run scope/error state.
2. Source same-size/restored-mtime in both separate processes and live watcher; atomic save with unchanged size/time, same-stat fake backend, write-revert, chmod/read failure, symlink target replacement according to supported semantics. Extend `TestSameSizeRestoredMtimeStillDirty`, `TestSourceHashUsesConsumedBytes`, `TestConsumedHashMatchesBytes` and `TestNoopDeltaDoesNotPublishOrAdvance`.
3. Deterministic watcher fake: event before/after registration, edit during baseline, late-delivered event after an empty drain, directory rename/move-in, final file deletion/restoration, overflow/error/disconnect, silent-loss audit, restart gap, dropped cursor history and changed root identity. Only a supported barrier may satisfy strict flush; otherwise assert reconciliation. Use real OS integration checks separately from fake queue tests.
4. During analysis and slow broker publication, edit the same and another file; every final change eventually reaches the next exact generation without clearing later dirty marks. Force bounded-queue overflow and backpressure. Interrupt before End journaling, after End journaling, after ack and before promotion, and during patch compaction; reuse existing journal fault/replay suites.
5. Extend `TestBuiltinHiddenInputDelta`, `TestSessionConfigPathsRetainPrunedConfig`, `TestManifestLockInputsAndPrecedence`, `TestConfigRediscoveryRejectsAddedPrunedConfigDuringRun` and TS config inventory tests with new nested/ignored/extended external config, missing config appearance, nearer lockfile, empty assets and inactive detector activation. Opaque custom extractor must visibly take fallback, never silently reuse.
6. Body edit with direct IO must parse only that file and avoid caller attribute rewrites (`TestDeltaBodyEditPublishesBoundedOwners`, `TestTSBodyEditDoesNotRerunMarkdown`). Structural tests cover long re-export chains, cycles, ambiguity creation/removal, candidate addition for previously unresolved references, changed import preference, rename/deletion and synthetic shared-owner removal. Count actual parse identities across expansion rounds and resolution owners, not only event count.
7. Retained cache immutability: repeated composition/delta sequences match cold results with no accumulated derived facts; changed synthetic contributor counts preserve other owners. Check optional full-snapshot accessor separately from summary-only Apply.
8. Real main revision transition fixture/harness (root owns Product): pin base and target revisions and effective scope; include multi-file add/delete/rename/re-export/config changes plus a separate dirty/untracked case. Measure fresh CLI, daemon bootstrap, warm idle, event-to-first-batch, event-to-all-broker-acks and durable promotion separately. Repeat and report spread, ratio to initial, memory, source/hash bytes, names visited, composition scope, state bytes/fsyncs, actual parse count and backlog delay. State whether checkpoint/audit costs occurred or were deferred; include steady-state amortized measurements and fallback cost. Do not hide reconciliation or background work outside reported latency/resource accounting.

Acceptance remains exact cold/delta equivalence under the local-fact contract plus repeated measurements against pinned old Enola on the same project/host/scope. A fast-path target can be subsecond small-change operation and near-zero idle service work, but this review does not establish either timing. Strict cold working-tree validation remains repository-sized without trustworthy prior observation; that limitation must be explicit rather than traded away through stat or Git shortcuts.
