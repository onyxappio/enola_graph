# Enola graphsession incremental architecture: independent design audit

Date: 2026-09-21. Scope: read-only architectural review of the working checkout, not approval of a forthcoming implementation. HEAD is d086926aca80975dde34094e99c84cce59fb1cd6; the relevant implementation is working-tree code, so HEAD alone is not its provenance. Read AGENTS.md, CONTRIBUTING.md, docs/STREAMING_INCREMENTAL.md, docs/benchmarks/PRODUCT.md, and the source locations below. No production changes, builds, tests, or benchmarks were performed. Root owns final measurements; Grok owns profiling/implementation.

## Assessment

The documented 7.757 s no-op and 9.133 s body delta are consistent with substantial whole-project work outside parsing. Source inspection establishes that work exists, but does not attribute measured seconds to individual stages. In particular, do not call the shallow FileState copy a full deep graph clone, and do not confuse the final selective owner encoding with full graph encoding: the expensive whole-graph stages are loading, fact reconstruction/cloning, composition, indexing and grouping before selective output.

A safe sequence is: eliminate no-op fact materialization; separate a small committed input manifest from graph payloads; narrow audited extractor input dependencies; then incrementally maintain composition and resolution indexes. Preserve content reads for every potentially relevant input in a fresh CLI invocation. A watcher or daemon may avoid reloads, but cannot silently substitute unreliable event delivery or mtime for strict detection.

## Prioritized changes

### P0 — Measure phase costs and preserve a strict control path

Instrument elapsed time and counters for identity/recovery, state read/decode, inventory walk, content hashing (files and bytes), configuration discovery/read, detection, local parsing, cached-record reconstruction, composition, reverse invalidation, owner index/grouping, source revalidation, state encoding/sync, and publication/ack completion. Track actual non-TS files read/parsed too: FilesParsed currently describes TS session parsing and is not evidence that only one source was read or one extractor did work. Keep instrumented runs separate from acceptance timings.

The warm process versus fresh CLI distinction must remain explicit. Watch currently calls Run on every tick (session.go:1519), reopening/recovering/reloading the session rather than keeping an incremental analysis resident. Root should measure separate CLI and resident operation separately if the latter is introduced.

### P1 — Put the no-op decision before graph construction and loading

Current path: Run opens/replays the journal and recoverAcknowledgedPending loads state; persist.go:readStateFile reads and unmarshals the entire JSON document. Product state is documented as 55.51 MiB. session.go:242 copies all FileState wrappers; reuseTSCache at approximately 430 clones cached facts through cloneTagged and applies IO; other extractors collect cached facts and synthetic provenance; newFiles and merged contributions are constructed. Only at approximately 781 does skipPublish return. No-op avoids buildIndex/groupOwners, but pays preceding materialization costs.

First, split planning from materialization inside the existing format: determine dirty inputs, enabled/detected extractor changes and framework/config invalidation, then return without building allFacts or newFiles if nothing can change. Preserve the public Result.Facts behavior deliberately: offer an explicit materialization option or a lazy snapshot accessor, and request facts only for callers that need them. Silently returning empty facts to an existing snapshot consumer would change an API contract.

Next, persist a compact input/identity manifest with generation, completion/run identity, schema and extraction version, effective configuration keys, input membership/content hashes/readability, extractor input digests and detection state. Load only this manifest on an ordinary no-op; graph payload remains lazy. The manifest must be the manifest of the *committed* graph, not a separately advanced sidecar. A missing, corrupt, mismatched or legacy manifest falls back to the existing validated load path, not success. Perform identity validation, journal replay and acknowledged-pending recovery before any early no-op decision; an apparently unchanged checkout can still have a pending broker generation to recover.

### P1 — Replace FileHashes(AllNames) with a proven input contract, not metadata trust

session.go:175-195 hashes production files, tests and every remaining AllNames entry. engine.go:1604 uses os.ReadFile plus SHA-256 for each file. AllNames means visited filenames before file-ignore filtering, not an exhaustive descent into pruned directories. This reads content of ignored artifacts purely to support conservative scanHash/context invalidation. inventoryDigest also repeatedly normalizes, deduplicates and sorts names.

Separate (1) discovery/name membership, (2) extractor content inputs, (3) required config/context files and (4) opaque plugin fallback inputs. Keep a whole-project filename walk where detection/link existence semantics require it, but hash content only for the union of relevant content inputs of all configured extractors and detectors. Unknown plugin dependencies retain conservative hashing; OwnedFiles/FileOwner describes output/cache ownership and is not sufficient proof of input closure. Disabled-but-configured detectors can require marker content too. Required files outside ordinary inventory, nested and extended config, Prisma/schema/template inputs and ignored detection markers must remain included.

A fresh strict CLI cannot avoid reading all potentially relevant bytes merely because size, mtime, Git HEAD or tracked status is unchanged. Same-size edits with restored mtime, dirty/untracked inputs and atomic replacement must still be detected. Use streaming hashing to bound allocation for large files, or captured bytes shared with extraction for files actually parsed; do not retain every artifact byte as a memory optimization. Parallel hashing is a measurement question: engine.go already documents a historical sequential-read advantage on a different project.

### P1 — Give non-TS extractors precise input hashes

session.go:294-307 and state.go:ownedExtractorContextNeed compare each owned extractor against fileSetHash (names *and content of every inv.Files file*). Thus a TS body edit invalidates unrelated active scopes. The subsequent complete factsFingerprint suppresses unchanged output but cannot undo extraction cost. No-owner extractors conservatively depend on scanHash. This explains why small output and low TS parse count are insufficient.

Introduce an optional, versioned input-dependency capability for audited extractors, retaining the conservative default for others. Separate content, name-set and context dependencies. Concrete audited example: mdintent.Extract creates newInScope(files), then reads markdown bytes; its document links depend on all walked file/directory names, not bytes of arbitrary TS targets. Its digest can include applicable markdown content plus exact extraction inventory names and configuration/detection context. A TS body edit should not rerun markdown; adding/deleting/renaming its link target must. Preserve _archive/_views exclusions and synthetic link coverage contributions. Do not simply remove ownedExtractorContextNeed globally: TestOwnedExtractorFileSetAddEqualsCold and other provenance regressions exist to protect non-owned inputs.

If one file needs two extractors, keep separate consumed hashes and contributions. Zero output is a valid cached result. Deleting the last detected input must retire previous owners and synthetic contributions. Narrowing detection cannot strand a prior extractor's graph.

### P2 — Incremental state storage and immutable contribution reuse

cloneFileState (owner.go:108) copies a wrapper and contribution maps, sharing TS and fact slices. The heavier repeated copies are reuseTSCache/cloneTagged and TS resultFromRecord/cloneFactSlice followed by another clone in ExtractSession's aggregation. ExtractSession still loops through all records and reconstructs allFacts even when only one file parses.

Keep file-local records immutable; copy only dirty contributions and mutation-bearing fact properties/relations. Audit applyLocalIO, tagRepo, Nuxt/router/Angular composition and synthetic aggregation before sharing: mutating aliased facts changes the previous checkpoint in memory and corrupts comparisons or retries. Separate raw local facts from derived composed facts; do not feed prior derived output back into local input.

For fresh CLI deltas, immutable per-file blobs plus a generation manifest (or an embedded transactional store) can avoid full graph JSON decode/rewrite. Store only changed blobs, reference unchanged ones, and persist compact resolution/composition summaries. Whole-state writePendingState currently JSON-encodes and fsyncs the entire next graph on every successful changed run. Introduce storage changes separately from resolver semantic changes to keep recovery testing tractable. Unreferenced pending blobs may be collected only after recovery can no longer require them; branch/fork manifests may share blobs without allowing writes to the base context.

### P2 — Incremental resolution must cover every relation kind

session.go:801 builds an index of allFacts and groups all owners before filtering to replacement scope. owner.go:434 resolves by target name, preferring same-repo candidates, and treats distinct candidate identities as ambiguity. Persist a compact name -> candidate identity/refcount index, plus relation target -> referencing owner index, partitioned by repository preference as needed. Update candidate membership on removed/added contributions. Re-encode all referencing owners only when their effective resolution result changes, plus owners whose local output changed. The reverse target index must include non-TS and synthetic relations, unresolved and ambiguous relations—not just FileRecord.Referenced or import edges.

Do not equate name stability with identity stability: a declaration can move file/kind or otherwise change identity without changing its displayed name. Do not collapse duplicate contributions to one count: removing one of two facts with the same identity must retain the candidate until the last contribution disappears. Ambiguous -> resolved, unresolved -> resolved, same-repo preference and disappearance of the preferred candidate all need tests. An affected owner must publish its complete replacement including unchanged facts contributed by other extractors.

The existing full index is conservative and relatively simple; retain it as a reference implementation/fallback until the new affected-scope logic is demonstrated. Merely keeping global buildIndex does not repair an omitted owner in replacement scope. Audit the scope closure independently.

### P2 — Separate local parsing, surface propagation and composition

invalidateTS already delays reverse closure for content-only edits until surfaceChanged; preserve that. ReverseClose constructs reverse dependencies and repeatedly scans the expanding dirty set. A maintained reverse adjacency index plus queue is cheaper and has clearer fixed-point behavior. Do not impose a one-hop limit: deletions, re-exports, ambiguous resolution and cycles need a sufficient closure. Conversely a local direct IO/property edit must not propagate through transitive callers.

ExtractSession recomputes GraphQL/gRPC aggregate indexes, router composition, coverage and modules from all cached summaries; a second invalidation round reruns this full reconstruction. CompositionSignature separately folds summaries, and ConfigInputPaths recursively walks for package/tsconfig inputs; config discovery occurs again before End. Maintain per-file composition summaries with counts/reverse participants and regenerate only affected composed owners. Global enabling switches (GraphQL presence), gRPC ambiguity, Nuxt name mappings, Angular templates and module coverage require explicit broader invalidation. Angular currently forces full extraction even for unchanged inputs; do not claim universal zero-parse no-op until its missing cached extras are handled or the limitation is explicit.

## Source consistency and crash safety

The current changed-run completion rereads every tsRecord and compares its hash, then rereads configuration/captured sources (session.go:885-918). That is additional whole-project IO beyond initial hashes. Do not simply delete it: it rejects changes to cached source while the run is in flight. To reduce it, define a verified snapshot/watch epoch or retain equivalent validation. Strictly consuming captured bytes and queueing subsequent edits is compatible with the documented mutable-worktree contract, but claiming an atomic snapshot of disk is not. Non-TS extractors that read os.ReadFile directly must also bind consumed hashes to their actual bytes before a narrowed digest is considered sound.

Preserve the durable order: persist pending graph+manifest; journal End; wait for all broker acknowledgments; require acknowledged End for that run; promote graph+manifest atomically; then reclaim safely. Empty unacked set is not proof of End. A fast manifest must never advance the base before the graph it describes can be replayed. Preserve exact message identities/payloads, bounded journal/backpressure, scope declaration before resolved writes, and fork/sink/context identity validation. No recommendation here justifies raising the spool bound or relaxing fsync/ack barriers.

## Focused acceptance cases

1. Separate CLI unchanged runs with actual full configured profile: zero file parses across extractors, zero events, unchanged generation and completed graph; demonstrate reduced decoded/materialized fact counts as well as time. Include missing/legacy fast manifest and unfinished pending recovery.
2. Same-size source edit with restored mtime; untracked relevant file; same-path atomic replacement; hash/read failure; configured ignored marker and external/nested config change. Each must detect correctly or explicitly fail, never report a false no-op.
3. TS body/local IO edit: parse only required whole files, no unrelated markdown extraction, no transitive IO attribute writes; exact direct io_direct/performs_io semantics. Body edit may change positions or other properties even if declarations stay stable.
4. Markdown target body edit versus target add/delete/rename; markdown content/property/line edit; final markdown removal/restoration; duplicate/shared contributions and synthetic coverage. All must equal fresh cold output.
5. A->B->C import/re-export chain and cycle: local property edit stays local; deletion/rename/export or resolution change refreshes the necessary closure. Add a competing extension/index file that changes resolution precedence of an already resolved import, not only a previously unresolved import.
6. Global same-name candidate creation/removal, duplicate identities, identity change with same name, ambiguous/resolved/unresolved transitions; include non-TS -> TS and synthetic -> file relations. Check complete incoming-edge owners, not only the changed declaration owner.
7. Enable/disable extractor; delete its final detected file; multiple extractors own one file; unknown extractor reads an unowned input. Retain conservative fallback behavior and provenance tests.
8. Extended/nested tsconfig, package detection, GraphQL enablement, gRPC ambiguity, router mount changes, final file in module deletion/restoration, Nuxt/Angular required input loss. Cache either correctly or announce a conservative fallback.
9. Edit during hash/parse/revalidation, including unchanged cached file mutation and A->B->A restoration: bind graph hashes to consumed bytes and refuse or schedule a subsequent generation consistently. Include non-TS consumed bytes.
10. Interrupt before pending persistence, before End journal, after End journal but before ack, after ack before promotion, and during graph/manifest promotion/GC. Restart through real journal replay and original Consumer; wrong-context/sink/fork state must fail safely.

For every changed case, apply initial plus deltas to the same reference Consumer and compare exact owned node/edge multisets to an independent cold run, including positions, properties, occurrence multiplicities and resolution. Same counts alone are insufficient. Root's repeated, sequential Product benchmark must retain pinned old/new scope, input revision and host, broker-confirmed completion, first batch, memory, files/bytes read, parsed files, event bytes and spreads. Report improvements against the current 7.757/9.133 s baseline as well as old Enola; no unmeasured subsecond claim is supported by this audit.
